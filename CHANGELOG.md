## [Unreleased]

### Added

- `repo ci wait [<branch>]` waits on the `ci` run of that branch's tip (default HEAD), up to 45 minutes, and exits 0 passed, 1 failed (the failed steps' logs follow), 2 superseded, 3 nothing to wait on (no run for the sha from any trigger, and the branch is neither the default branch nor has an open pull request), 4 error. A missing gh login, missing run, unpushed sha, unreadable HEAD or timeout is now exit 4, not 1, and `wait a b` exits 2. Each outcome is recorded in `.tmp/repo/ci/<sha>.json` under the main checkout. A run dispatched on a branch with no pull request is waited on. `repo release` and its gate report exit 3 as `no CI will run` with the reason. `/commit-push` and `/commit-push-deploy` run it in the background after the push and loop: on a failure fix in a new worktree, push and wait again, and after three failed rounds on one job report the logs and stop.
- A push gate holds the parent's Stop while the newest pushed commit of a branch has no ci result. The hook notes every `git push` of a session (also the `-C <dir>` and `cd <dir> &&` forms), and Stop blocks with one of three lines until the sha passed, had nothing to wait on, errored, or failed three rounds on one job. It caps at 6 blocks a turn on its own `push-block` stamp, apart from the ask and away cap. A subagent's Stop is unchanged.
- With a root `Cargo.toml` under the `release` pack, the generated nightly runs cargo-mutants 27.1.0 (cargo's own test runner, so doctests count) in shards through `repo mutate --rust --shard i/n`, and `repo mutate check` holds each crate dir to its floor in `mutation-floors.json` beside the TypeScript packages; `repo mutate check <dir> --write` raises a floor and never lowers it. `repo mutate --rust` runs it locally in a throwaway clone of HEAD, a Rust-only repo needs no Stryker, and `#[mutants::skip]` and `#[cfg(test)]` code produce no mutants. Install it with `cargo install --locked cargo-mutants@27.1.0`; the agent rule `agents/rules/rust.md` describes it.
- With a root `Cargo.toml`, `repo release api` runs `cargo semver-checks check-release` (cargo-semver-checks 0.51.0) on each workspace crate that publishes to crates.io, against the highest non-yanked crates.io version at or below the checkout's; a crate crates.io does not have yet is skipped. When the checkout version is above that baseline the bump decides, otherwise the crate's commits since the baseline was published do: from 1.0 a breaking `!` commit allows a major and `feat` a minor, before 1.0 a breaking commit allows a minor, else a patch. To ship a break, bump the version or mark a commit under that crate breaking with `!`. The generated `ci.yml` runs it in a `semver` job, and the agent rule `agents/rules/rust.md` describes it.
- With a root `Cargo.toml`, `repo ci` runs a `rust tests` gate: `cargo nextest run` (cargo-nextest 0.9.151), `cargo test --doc` when a target has doctests, and under coverage `cargo llvm-cov nextest` (cargo-llvm-cov 0.9.1) with each `.rs` file held to its `coverage.floors` row on lines, functions and regions; `--no-coverage` skips the measurement. `repo coverage` writes and only raises the `.rs` rows, the generated toolchain gains `llvm-tools-preview`, the generated `ci.yml` installs nextest and llvm-cov, and the agent rule `agents/rules/rust.md` describes the tests.
- With a root `Cargo.toml`, clippy runs with `--locked` and `bun repo check` fails a missing, stale or untracked `Cargo.lock` with one line. Under the `standards` pack it also fails a publishable crate missing `license`, `description`, `repository` or `rust-version`; cargo-deny errors under a generated, untracked `deny.toml` (permissive licenses only, no unknown registries, no git sources, no wildcard versions); cargo-shear findings (a deliberate unused dependency goes under `[package.metadata.cargo-shear] ignored`); and a cargo-deny or cargo-shear that is missing or not at the pinned 0.20.2 and 1.14.0. A failed advisory-database fetch is one line asking for the network. `bun repo sync` ignores `target/`, and the generated `ci.yml` installs cargo-deny and cargo-shear (`taiki-e/install-action` and `Swatinem/rust-cache`, SHA-pinned) after `bun install` in `test` and `no-node`, and adds an `msrv` job running `cargo hack check --rust-version --workspace --locked --ignore-private`, which prints `no publishable crate` and passes when every crate is private. `msrv` joins the required status checks.
- A repo with a root `Cargo.toml` and the `standards` pack now gets Rust standards. `repo sync` writes untracked `rust-toolchain.toml` (rust 1.99.1 with rustfmt and clippy, profile minimal), `rustfmt.toml` (rustfmt's defaults) and `clippy.toml` (unwrap and expect allowed in tests, 30 lines and 3 arguments per function), and the agent rule `agents/rules/rust.md` for `**/*.rs`. `repo check` and `repo lint --baseline` count `cargo clippy --all-targets --all-features` at `clippy::pedantic`, `unwrap_used`, `expect_used`, `undocumented_unsafe_blocks`, `unnecessary_safety_comment` and `unreachable_pub` as `clippy(<lint>)` and `rust(<lint>)` hits, plus three source rules: `repo(rust-lint-attribute)` for `#[allow]`, `#[expect]`, `#[warn]`, `#[deny]` or `#[forbid]` in code, `repo(rust-block-comment)` for any `/* */`, and `repo(rust-max-lines)` for a file over 200 code lines; the baseline, the excess report and the skip report treat them like every other hit, and a compile error is a check problem, not a hit. `repo lint` prints each Rust hit as `file:line:col: error rule: message` after oxlint, and `repo lint <paths>` runs only the source rules on the `.rs` paths; `repo turn` never runs clippy. `repo fmt` also runs `cargo fmt --all`, with `--check` when you pass it. `lint.skip` takes `clippy/<lint_name>`, `rust/<lint_name>` and the three `repo/rust-*` names, only in a repo with a root `Cargo.toml`; a misspelled one fails as `has no hit`. With a `Cargo.toml` and no `cargo` on PATH, `repo check`, `repo lint` and `repo fmt` fail with `Cargo.toml is here but cargo is not on PATH; install rustup from https://rustup.rs`. A repo without a root `Cargo.toml` is unchanged.
- `repo/native-path-separator` reports `.endsWith`, `.startsWith`, `.includes`, `.split`, `.indexOf` or `.lastIndexOf` called with a string or template literal holding `/` or `\` on a value that is provably a native path: a `path.join|resolve|dirname|normalize|relative` call (never `path.posix`), `process.cwd()`, `import.meta.dirname`, `__dirname`, `tmpdir()`, `fileURLToPath()` and the like imported from `node:os`, `node:url` or `node:fs`, anything named `cwd`, and a `const` set to one of these. The path uses `\` on Windows, so the check passes on Linux and fails only on Windows CI; the message names `path.basename`, `split(path.sep)` and `.replaceAll(path.sep, "/")` as the fix. After your next `repo sync` turns it on, fix the reports it finds.
- Under the `docs` pack `repo sync` writes a `repo:available` section into `references/INDEX.md`: each published `@workerstack/*` package that the root and workspace packages do not install, with its npm link and what it does, read from the new `@workerstack/references` dependency's index; installed packages stay under `repo:stack`.
- `repo docs --check` checks each doc root (the root and each workspace package with `references/INDEX.md`): every reference file is listed in its folder's INDEX, every relative link resolves (a missing `node_modules` package is named), every export of a public package is named in a reference, every `ts` block type-checks against the installed packages and every `ts run` block runs, and a public package's dry-run tarball holds its listed references and its exports hold `./references/*`; each finding names its file, line and fix. `repo docs` runs `repo sync` first, and `repo ci` runs a `docs` gate after `check` under the `docs` pack. Under that pack `repo sync` also generates each public doc root's `README.md` from its INDEX (a contents list, then each reference file), refusing to replace a hand-written one. The package now exports `./references/*`.
- `repo/no-block-comment` reports a `/* */` comment that stands alone on its lines and fixes it with `repo lint --fix` into one `//` line per line of text at the same indent; `/** */` docs, a `/* */` inside a line (`x as /* why */ T`, `/* @__PURE__ */`), a first-line `/*!` license and config comments (`global`, `exported`, `eslint`) stay. `repo fmt` makes the same conversion in tracked `.json` and `.jsonc` files with comments (fixtures dirs excepted), `repo fmt --check` lists them, and `repo turn` converts them before the key sort. After your next `repo sync` turns it on, run `repo lint --fix`.
- `repo check` fails when a public package (the root or a workspace member with `"private": false`) lists a private workspace package in `dependencies`, `peerDependencies` or `optionalDependencies`, naming the edge and the fix, since a consumer cannot install it; `repo/boundaries` fails when shipped code of a public package (its `files`, plus the `main`, `module`, `types`, `bin` and `exports` targets, never a test or fixture) imports a package that only its `devDependencies` declare.
- The new `ci: { checks: { "container-images": ["bun", "scripts/check/container-images.ts"] } }` key in `workerstack.config.ts` names commands, each an argv array run from the root without a shell, that `repo ci` runs after its own gates in config order; each prints a line and a time like a gate, shows its output when it failed (`<name> failed (exit N)`, or `<name> failed (<command> not found)`), and counts in the summary and the exit code. A name must be kebab-case and cannot be `check`, `fmt`, `typecheck`, `tests` or `packages`.
- `repo update [--check] [<name>…]` reads the registry's `latest` for every catalog entry (default and named) and every plain direct version in the root and workspace manifests, and lists each that is behind with where it lives; without `--check` it writes each new version into that one place, keeping the `^`, `~` or exact prefix, formats the changed manifests and runs `bun install`. Ranges, and names the registry does not have, are listed as skipped; protocols, tags and peer dependencies are left alone; a prerelease above `latest` is never downgraded; a registry that does not answer fails the run before any write. `repo remove <name>…` drops each name from every dependency field of every workspace manifest, every catalog, and the root's `overrides`, `resolutions`, `trustedDependencies` and `patchedDependencies` (deleting the patch file), formats, and runs `bun install`.
- `repo clean --build` removes the build output git ignores (`.next`, `.open-next`, `.turbo`, `.wrangler`, `.tanstack`, `.start`, `.vite` and `*.tsbuildinfo`, at any depth) and `repo clean --deps` also removes every ignored `node_modules`; neither touches a tracked or unignored path, neither runs the `.tmp/repo` sweep, `--dry-run` lists what they would remove, and both flags together exit 2. The new `clean: { build: [".flare"] }` key in `workerstack.config.ts` adds dir names beside the built-in ones.
- `repo link <name>` packs the sibling checkout that publishes a package (or, given a sibling directory's name, each package it publishes that this repo depends on) with `bun pm pack` and swaps it into the install root's install directory without touching package.json or `bun.lock`; `repo link status` lists the links, `repo unlink <name> | --all` puts npm back, and `repo sync --postinstall` reapplies the links after every `bun install`. The `link` key in `workerstack.config.ts` maps a package to a checkout that is not a sibling. Under the `standards` pack `repo sync` writes `.githooks/pre-push`, which runs `repo link --pre-push` and refuses a push while a public package here depends on a linked one.
- Under the `workspace` pack `repo sync` writes an ignored root `vitest.config.ts` listing each package's `vitest.config.ts` under `projects` and an ignored `turbo.json` with `typecheck`, `test` and the config's `turbo.tasks`, and ignores `.turbo/`; `repo check` names a package with a `vitest.config.ts` or `tsconfig.json` but no `test` or `typecheck` script; `repo ci` typechecks the root and runs `turbo run typecheck test` from turbo's platform binary, passing `--no-coverage` and the skip report through to each package's run, and the generated `ci.yml` restores `.turbo/cache` and saves it only on main.
- The `workspace` pack makes `repo check` hold a bun workspace to a catalog-only, one-version, dev-only-root layout: every package dependency is `catalog:` (or `workspace:`) and resolves to an entry in `catalog` or `catalogs`, written top level or under `workspaces`; `bun.lock` resolves each dependency to one version, and a name with two gets a line naming the parent that pulls the stray copy and the `overrides` entry that fixes it; the root has no `dependencies`, `peerDependencies` or `optionalDependencies` and only `@workerstack/repo` in `devDependencies`. A missing `bun.lock`, a binary `bun.lockb` or a `bun.lock` that does not parse is a line too, and each line names its fix.
- Under the `release` pack `repo check` holds a public package's `keywords` to GitHub's topic shape: 1 to 20 unique entries in code-unit order, each lowercase letters, digits and dashes, starting with a letter or digit, at most 50 characters; each problem is a line with the exact fix, such as the sorted list to write.
- `repo github [--check]` makes the GitHub repository match package.json and the generated CI through `gh api`: a `main` ruleset (no deletion or force pushes, a pull request with every CI job as a required GitHub Actions check) and a release-tag ruleset (only an admin creates, moves or deletes `v*` and `*@*` tags), both letting admins bypass, plus private vulnerability reporting, Dependabot alerts, and the description and homepage from `description` and `homepage`, and the topics from `keywords` as written; keywords that are not 1 to 20 unique, sorted GitHub topics are refused with the lines `repo check` prints. A second run changes nothing; `--check` and `repo check` print each setting that drifted and skip, without failing, when gh cannot read the settings.
- `repo release api [--against <tarball>]` installs the packed checkout beside the last released version and compares what each code subpath exports with the TypeScript checker. A removed or narrowed name or subpath needs a breaking commit since that version's tag, and an added or widened one a `feat` or breaking commit; the `consumer` job in ci.yml now checks out with full history and runs it after `repo release consumer`.
- `repo/public-jsdoc` requires a written doc on everything a public package's `exports` reach: each declaration and each member a consumer can see. It reports a doc that is missing, empty, only restates the name, cites a plan, slice, roadmap or decision number, or shares a line with code, and a type left to inference; a form it cannot follow, like `export =` or a namespace, is reported too. A private package has none. After your next `repo sync` turns it on, seed the reports that already exist with `repo lint --baseline`.
- `repo/deprecated-replacement` reports a `@deprecated` tag that names no replacement; write "use `newName` instead" or `{@link newName}`. It applies to every JSDoc block, public or not. After your next `repo sync` turns it on, seed the reports that already exist with `repo lint --baseline`.
- Under the `release` pack with a public package, `repo check` requires complete `package.json` metadata (description, keywords, MIT license, author, `git+https` repository, homepage, bugs, `type: module`, engines, exports with `types` first and `./package.json`, files, `publishConfig.access: "public"`) and an MIT `LICENSE` naming the owner; the new `owner: { name, github }` key in `workerstack.config.ts` names the author.
- `repo release consumer` also runs publint (strict, suggestions fail) and attw on the tarball, ignoring the node10 and CommonJS resolutions an ESM-only package never serves.
- `repo sync` writes `SECURITY.md`, `CONTRIBUTING.md`, `.github/CODEOWNERS`, the pull request template and the bug report issue form for a public package with an `owner`, and refuses to replace a hand-written copy.
- `repo release consumer [<tarball>]` installs the packed tarball into an empty project with `bun add`, imports every subpath its `exports` reach and type-checks every `types` target; the `release` pack adds a `consumer` job running it to ci.yml for a public package.
- `repo check` fails when `node_modules/@workerstack/repo` is behind the `latest` on the registry bun installs from, and notes it when the registry does not answer.

### Changed

- Every JSON file `repo` writes (`repo sync`, `repo fmt`, `repo coverage`, `repo init`, migrations) now has its keys sorted by code unit, and `repo fmt` sorts those it formats, JSON and JSONC files alike with each comment moving with its key, with oxfmt's `sortPackageJson` ordering package.json. Run `bun repo fmt` once after upgrading so your JSON files match, then `bun repo sync`, since sorting `.repo/hooks.jsonc` or `.repo/mcp-policy.jsonc` reorders the generated hook files; a comment about a whole block (the hooks, above the first event) moves with that key, so put it above the block's own key first.
- Every file `repo sync` writes whole now opens with one `@generated by @workerstack/repo` header line (as `#`, `//` or `<!-- -->`, after a shebang in a hook; none in strict JSON or a file with frontmatter) in place of the old `Generated by …` wordings, and every sync leaves it read-only (0444, 0555 for a hook) even when its bytes did not change, so a hand edit fails in the editor instead of being lost at the next sync; `repo tasks` and the lessons index do the same, and a block-managed file such as `.gitignore` stays writable. A tracked file with that header (or an old wording) that the new version no longer writes is removed by `repo sync`, and named by `repo sync --check`, even in a fresh clone with no `.repo/tmp/sync.json`; to keep a copy of one, change its first line. Files under a `fixtures` folder are never removed.

### Fixed

- `repo job --job search` on Windows no longer leaves a shimmed `rg` running after its output overflows; the shim's children are ended by parent pid once the shim is gone.

## [0.1.0] - 2026-11-10

### Added

- `workerstack.config.ts` with `defineConfig` from `@workerstack/repo` declares a repo's packs, and an unknown key or pack fails with a message that names it. `repo sync` writes `bunfig.toml` (hoisted linker, and no auto-install, so a missing import fails instead of fetching from the registry), the `# >>> @workerstack/repo` block in `.gitignore`, and the `repo:packages` and `repo:stack` sections of `references/INDEX.md`. It checks everything before writing anything and refuses to overwrite a hand-written `bunfig.toml`. `repo sync --check` fails on drift, and `repo sync --postinstall` prints errors without failing the install. `repo init` writes `workerstack.config.ts` when it is missing and adds `repo sync --postinstall` to the `postinstall` script.
- Strict tsconfig bases with ts-reset built in: extend `@workerstack/repo/tsconfig/base`, `bun`, `worker` or `web` and list your sources under `include`. `JSON.parse`, `.json()` and similar calls then return `unknown` instead of `any`. The `bun` base brings Bun's types with it. The `worker` base needs `@cloudflare/workers-types` installed in your repo.
- A shared vitest preset: `defineProject` for a package's `vitest.config.ts` and `defineConfig` for a root config, both from `@workerstack/repo/vitest`. They set 5s test and hook timeouts (60s on Windows) and the forks pool, and `defineConfig` adds istanbul coverage. Both set `deps.interopDefault: false`, which bun needs to import packages like zod. Your own settings win. Install `vitest` and, for coverage, `@vitest/coverage-istanbul` (both ^5.1.0), and run the tests with `bun --bun vitest`.
- `repo check` now also fails when a tsconfig drops ts-reset: one that sets `files`, which replaces the base's, or one that extends no base. It prints one line per file and exits 1. A solution-style root with `"files": []` and `references` passes. The `repo` command now runs on bun, so bun must be on your PATH.
- `repo release [--stable | --pre <id>]` releases the root package of a public repo with the `release` pack. It bumps the version from the Conventional Commits since the last tag (from 1.0 a breaking commit is a major, a feat a minor, a fix, perf or revert a patch; below 1.0 a breaking commit is a minor and the rest are patches), moves `## [Unreleased]` in CHANGELOG.md under the new version, commits `chore: release <name>@<version>`, pushes, waits on CI for that commit and only then tags `<name>@<version>` and pushes the tag. Run it again after a red or missing CI result: it finishes the same version, folding new Unreleased entries into it, instead of bumping twice. It refuses with one line, before writing anything, on a dirty tree, another branch, a main that differs from origin, a missing gh login, nothing to release, an empty Unreleased, a private package, a 1.x `--stable` and a tag that exists.
- `repo release wait <name>@<version>` polls npm every 10 seconds for up to 15 minutes and prints `published <version> under <tag>`, or `published <version>` when no dist-tag points at it.
- `repo check` holds a public root's CHANGELOG.md to Keep a Changelog: a dated `## [x.y.z] - YYYY-MM-DD` heading, the six section names, versions newest first and an `## [Unreleased]` section.
- The commit-msg hook refuses a feat, fix, perf or breaking commit that stages a file of a public package without staging that package's CHANGELOG.md.
- `repo sync` checks every output against its format, and the `.repo/` directory against its closed layout, schemas, links and size budget, before it writes anything, and then writes all of it or none. It also writes `.gitattributes` (generated files marked `linguist-generated`) and the editor settings that make them read-only, and refuses a nested ignore file. A rule can be scoped to `paths`, and an override has to replace a stock rule, subagent or skill. Each workspace package gets its own agents file, scoped rules, nested skills and a dependency index.
- `repo sync` writes `.oxlintrc.json` and `.oxfmtrc.jsonc`, and `repo lint` and `repo fmt` run them. The lint plugin refuses module side effects, boundary breaks, magic numbers and untyped compared strings, an `as` cast without a reason, a file whose name does not match its export, an unticketed todo, commented-out code, a mock of the module under test and a v8 ignore. `lint.skip` in `workerstack.config.ts` records a reasoned exception and fails when it goes stale. The counts the lint finds are held in `.repo/lint-baseline.json`, which can only shrink. `repo check` refuses rule-disable and ts-ignore comments, a manifest with a wrong `private`, `sideEffects` or unpinned bun version, environment reads outside `cli/env.ts`, and a tsconfig that no gate runs. A strict `src` tsconfig is typechecked, `reject.ts` type tests run, and each exported type guard needs a test that rejects.
- `repo turn` runs the gates for one change, and the generated `.githooks/pre-commit` and `.githooks/commit-msg` run it and check commit scopes and size against the `commit` limits in `workerstack.config.ts`. A feat or fix commit is refused unless a changed test fails without its source change. Test-run floors, known failures and the lint baseline are ratcheted against main, and a floor is raised and never lowered. A test run fails when it leaves a temp dir behind or skips a test for a reason that is not the platform.
- `repo ci` runs every gate in one call, and `repo check` refuses a root script that chains them. `repo check` also runs knip from a generated config, where each `knip.ignore` entry carries a reason and fails when stale, and runs actionlint. Under the release pack `repo sync` writes `.github/workflows/ci.yml` with pinned actions: it tests on three operating systems, checks every pushed commit and compares each OS's skips, and `repo ci wait` waits for the run of HEAD. `repo mutate` runs Stryker under bun in a throwaway clone with score floors, and `repo sync` writes `.github/workflows/nightly.yml` with sharded mutation floors and your live tests. `repo persist` saves temp files into the repo.
- With the `release` pack and `"private": false`, `repo sync` writes `.github/workflows/release.yml`. A `<name>@*` tag push, or `gh workflow run release.yml -f tag=<name>@<version>`, runs three jobs on that tag. `gate` checks that the tag equals the version in package.json at the tagged commit, that CHANGELOG.md has that version's section, that the commit is on the default branch and that its CI passed. `publish` packs with `bun pm pack`, refuses a packed `catalog:` or `workspace:` version, skips a version npm already serves and publishes through npm trusted publishing with no npm token, under `next` for a prerelease. `github` creates the GitHub release from the changelog section. A hand-written `release.yml` is refused. The jobs are also commands: `repo release gate | pack | publish | github <name>@<version>`, and `repo release help` lists them. A package that is not on npm yet cannot publish from CI; `publish` prints the steps: `npm login`, `bun repo release publish <name>@<version>` at the tag on your machine, then add the trusted publisher.

### Changed

- `repo doctor` no longer has a `node` row or node install hints, and `@workerstack/repo` no longer lists node in `engines`: nothing in it needs node. Bun is the only runtime it checks.
- Agents can remove any managed worktree and delete any `wt/*` branch; the gate guards only the default branch and force pushes.
- **Breaking:** the agent trees are generated and ignored. `repo sync` builds `AGENTS.md`, `.mcp.json`, `.claude/`, `.codex/`, `.agents/`, `.grok/` and `.cursor/` from `node_modules/@workerstack/repo` plus your `.repo/` into a staging dir, writes them, records them in `.repo/tmp/sync.json` and removes what drops out; in a consumer they are gitignored and every `bun install` recreates them (this repo still commits its own). `.repo/` holds the repo's own content: `rules/`, `subagents/`, `skills/`, `lessons/` (moved from `.rulesync/lessons/`), `settings/claude.json`, `hooks.jsonc`, `mcp-policy.jsonc` and `permissions.json`. `agents.hosts` in `workerstack.config.ts` picks the hosts to generate for (default: all five), and `agents.skills` enables the optional skills `google-workspace`, `listen`, `speak` and `clasp`, replacing `.rulesync/repo.features.jsonc`. `repo init` copies nothing: it writes `workerstack.config.ts` and `package.json`, then installs. The first `repo sync` in a repo an older init copied moves your own rules, subagents, skills, settings keys, `AGENTS.md` text, lessons, references, hooks, MCP policy and packs into `.repo/`, `references/` and `agents.skills`, untracks the generated paths and removes the copied `.rulesync/`; a destination that already exists with other text stops it with one line naming both paths, and `repo sync --check` reports the pending steps. `rulesync` is now a dependency of `@workerstack/repo`, since the install-time sync runs it. `repo generate`, `repo upgrade`, the `repo:rulesync:*` package scripts and the feature-packs file are gone: upgrade by bumping the dependency and running `bun install`, and regenerate with `bun repo sync`.
- **Breaking:** every script, hook and the CLI is TypeScript run by bun. `.rulesync/scripts/*.mjs` became `.rulesync/scripts/*.ts`, the grok hooks became `.grok/hooks/*.ts`, and the bin is `bin/repo.ts`. Generated hook commands read `bun "$d/…ts"`, and `.githooks/commit-msg` runs under `bun`. The old `.mjs` paths are gone; run commands as `bun repo <cmd>`. A consumer's own hook script keeps whatever extension bun runs. `repo doctor` gains a `bun` version row and finds node only on your PATH.
- The stock references moved from `.rulesync/reference/` to `references/` and ship in the package. Agents read them from `node_modules/@workerstack/repo/references/`, so `AGENTS.md` and the skills point there, and `repo init` no longer copies them. `law.md`, `skills-map.md` and `refs-map.md` are gone: `references/INDEX.md` holds the catalogs in its `repo:skills`, `repo:refs`, `repo:packages` and `repo:stack` sections. The first `repo sync` in a repo an older init copied removes the unchanged stock copies in `.rulesync/reference/` and moves each file or section of yours to `references/`.
- The `repo` bin runs on bun.
- Scripts and hooks run through the `repo` bin. Agents and people run `bun repo <cmd>` (`job`, `worktree`, `lessons`, `browser`, `google-workspace`, `jev`, `listen`, `speak`, `setup`, `doctor`, `clean`, `sync-globals`, `purge-mcps`, `tasks`, `map`), and every generated hook runs `"$d/node_modules/.bin/repo" hook <name>`, which prints `run bun install` and exits 1 in a checkout with no install.
